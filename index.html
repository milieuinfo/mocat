Simulation model vocabulary and API

MoCAT is a vocabulary for describing simulation models and an open API specification for interacting with simulation tools. This document lists the requirements, defines the vocabulary and API and provides an implementation report.

A simulation model is a tool to make a digital representation of a real-world phenomenon in nature, within a population, in a transport network, etc. We use simulation models to better understand observations of the past or to study the impact of changes in the future.

A common vocabulary for describing simulation models on the Web enhances its discoverability and automation potential. A generic API makes it possible to interact with simulation models in a standardized way, which can considerably reduce the effort required for a consumer to interact with a new provider.

Requirements

Although generally applicable, our source of requirements for this vocabulary originates from the domain of spatial planning and environmental permit management in the public sector. In both fields, a wide variety of simulation models are being used to assess the environmental impact of changes on, for example, traffic flows, air quality, water quality, noise, erosion, water levels, or emission of greenhouse gasses. In this context, we look at distributed systems: the systems for running simulation models are separate from the system of environmental permit management or spatial planning. This stems from the variety and complexity of simulation models, making it impractical to embed them in a monolithic system. Another reason is that there are typically multiple service providers (both businesses or public administrations) that provide specific simulation models. The impact assessment can be carried out before an environmental permit is formally requested to pre-assess the impact of the proposed changes (preparatory phase), or after the formal request has been submitted to underpin the decision process (evaluation phase). The simulation runs that are used in the decision-making process must be reproducible; this requires that all information regarding input datasets, context and exact model version is persisted and available for inspection. Depending on the context, the impact assessment can be carried out by the public administration, business or citizen.

Discover simulation models

Users must be able to discover simulation models by searching for and comparing simulation models using various descriptive metadata fields of which title, description, download URL and service endpoint are the most important. Other fields can be keywords, themes, usage constraints, ownership, licensing information, quality assessments [[VOCAB-DQV]], compliance with standards, source code repository URL, release URL, invocation mode (whether results of a simulation run are presented synchronously or asynchronously to a user).

A simulation model is the whole of method, algorithm, implemented in software, documentation, etc. A simulation model can be used as software or as a service.

In the domain of environmental impact assessment, simulation models can be catalogued in an (open) data catalogue. The need for enhancing the discoverability of simulation tools stems from the fact that there is an increasing number of providers and consumers.

Test interoperability of input datasets

A simulation model service may have several types of input data:

  • Spatial data: transport networks, spatial features, topological relationships
  • Entity definitions: nodes, machines, people, vehicles
  • Physical properties: noise characteristics, material characteristics, carbon storage parameters, etc.
  • Initial state: starting positions, starting inventory
  • Behavioural characteristics: e.g. travel demand (origin-destination matrices), driver behaviour
  • Run configuration: key-value settings that control a single simulation run
  • Scenario data: change of which the impact is assessed: for example, reforestation on CO2 emissions, buffer zones on soil erosion, or the creation, update and removal of roads in a transport network. Particularly, this input is often provided by the consumer of a simulation model.

Users must be able to assess via automated reasoning which input datasets are compatible with a simulation model based on the data specification.

In the context of spatial planning and environmental permit management, the consumer of a simulation model most often only needs to be concerned with providing the correct scenario data to the simulation model. Each simulation model service has a different way of encoding these scenarios in data.

Start a simulation run via a universal interface

It must be possible to run simulation models via a universal Application Programming Interface (API). The input and output parameters of the API methods are based on a common metamodel. A user can configure and execute a simulation run via a standardized interface. The execution must be asynchronous, allowing for manual interventions (e.g. calibration of input data) prior to executing the model.

Reproduce a simulation run

Metadata captures version history, parameter sets, data provenance, and software dependencies so that simulation results can be reproduced, audited, or certified, even when original creators are no longer involved. [[PROV-O]]

In the context of spatial planning and environmental permit management, this use case is important.

Vocabulary overview

MoCAT is organised in three layers, which are all visible in the end-to-end example in this document:

  • Plan layer: the [=simulation model=] (a prov:Plan) and the [=data specification=]s (p-plan:Variable, expressed as [[SHACL]] shapes) of its inputs and outputs.
  • Execution layer: the [=simulation run=] (a prov:Activity) and the software [=agent=] that executed it.
  • Data layer: the input and output [=dataset=]s of a run, each with one or more dcat:Distributions.

Vocabulary specification

The MoCAT vocabulary makes use of the [[VOCAB-DCAT-3]], [[PROV-O]], and [[P-PLAN]] specifications. The MoCAT vocabulary specification is available at mocat-ontology.ttl. A complete end-to-end example (Traffic Scout) is used throughout this section.

Class: Cataloged Resource (dcat:Resource)

A cataloged resource is a dcat:Resource: anything that can be described in a catalog [[VOCAB-DCAT-3]]. The [=catalog=], [=simulation model=], [=data specification=], [=simulation run=] and [=dataset=] classes are subclasses of cataloged resource and inherit the properties below. They are therefore not repeated in the sections of these classes. A [=distribution=] and an [=agent=] are not cataloged resources.

omg-simulationmodel:traffic-scout
    dcterms:title       "Traffic Scout"@en ;
    dcterms:description "Traffic Scout is a traffic simulation model ..."@en ;
    dcat:keyword        "traffic"@en, "simulation"@en ;
    dcat:theme          <http://www.eionet.europa.eu/gemet/concept/7702> ;
    dcterms:publisher   ex:TML ;
    dcterms:issued      "2026-03-15"^^xsd:date ;
    dcterms:modified    "2026-03-15"^^xsd:date .

Property: title (dcterms:title)

A title of a [=cataloged resource=] is a name given to the resource.

  • RDF property: dcterms:title
  • Domain: dcat:Resource
  • Range: rdf:langString

Property: description (dcterms:description)

A description of a [=cataloged resource=] is a free-text account of the resource.

  • RDF property: dcterms:description
  • Domain: dcat:Resource
  • Range: rdf:langString

Property: keyword (dcat:keyword)

A keyword for a [=cataloged resource=] is a free-text tag describing the resource.

  • RDF property: dcat:keyword
  • Domain: dcat:Resource
  • Range: rdf:langString

Property: theme (dcat:theme)

A theme for a [=cataloged resource=] is a concept from a controlled vocabulary that categorizes the resource, for example the EU data themes or [[GEMET]]. For a [=simulation model=] it is recommended to include the simulation concept from [[GEMET]].

  • RDF property: dcat:theme
  • Domain: dcat:Resource
  • Range: skos:Concept

Property: publisher (dcterms:publisher)

The publisher of a [=cataloged resource=] is the organisation that makes the resource available.

  • RDF property: dcterms:publisher
  • Domain: dcat:Resource
  • Range: foaf:Agent (typically foaf:Organization)

Property: issued (dcterms:issued)

The issued date of a [=cataloged resource=] is the date of its formal issuance.

  • RDF property: dcterms:issued
  • Domain: dcat:Resource
  • Range: xsd:date

Property: modified (dcterms:modified)

The modified date of a [=cataloged resource=] is the date of its most recent change.

  • RDF property: dcterms:modified
  • Domain: dcat:Resource
  • Range: xsd:date

Class: Simulation Model (prov:Plan)

A simulation model is a tool to make a digital representation of a real-world phenomenon. Its class is mocat:SimulationModel, a subclass of prov:Plan, p-plan:Step and dcat:Resource ([=cataloged resource=]). Instances should also be explicitly typed as prov:Plan and p-plan:Step, so that they can be found without inference (see the SPARQL query in the implementation report).

A simulation model may have a basis in physics, math and/or statistics. In addition to this theoretical foundation, the simulation model is usually implemented in source code and software. We see the simulation model as the whole: the mathematical or physical model, the algorithm, and the software that makes it executable. 

omg-simulationmodel:traffic-scout
    a                   mocat:SimulationModel, prov:Plan, p-plan:Step ;
    dcterms:title       "Traffic Scout"@en ;
    dcterms:description """Traffic Scout is a traffic simulation model developed by Transport & Mobility Leuven (TML).
It supports scenario calculations of multimodal traffic flows (car, truck, bicycle) at the mesoscopic level."""@en ;
    dcat:landingPage    <https://www.tmleuven.be/en/navigation/Traffic-Scout> ;
    dcat:landingPage    <https://traffic-scout.net/> ;
    dcat:keyword        "traffic"@en, "simulation"@en, "transport planning"@en, "traffic assignment"@en ;
    dcterms:publisher   ex:TML ;
    dcat:theme          <http://www.eionet.europa.eu/gemet/concept/7702> ;
    dcat:version        "3.0.4" ;
    dcterms:issued      "2026-03-15"^^xsd:date ;
    dcterms:modified    "2026-03-15"^^xsd:date ;
    mocat:input         omg-schema:TransportNetworkSchema ;
    mocat:input         omg-schema:OriginDestinationMatrixSchema ;
    mocat:input         omg-schema:RunConfigurationSchema ;
    mocat:input         omg-schema:TrafficChangeScenarioSchema ;
    mocat:output        omg-schema:SimulationOutputSchema .

ex:TML
    a             foaf:Organization, prov:Agent ;
    foaf:name     "Transport & Mobility Leuven"@en ;
    org:identifier "BE0476.966.024" ;
    foaf:page     <https://www.tmleuven.be> .

Property: landing page (dcat:landingPage)

A landing page of a [=simulation model=] is a web page that gives access to the model or to information about it, for example a product page. A model can have several landing pages.

  • RDF property: dcat:landingPage
  • Range: foaf:Document

Property: version (dcat:version)

The version of a [=simulation model=] is the version of the released software. It should equal spdx-sw:packageVersion of the [=agent=] that executes the model.

  • RDF property: dcat:version
  • Range: rdfs:Literal

Property: input (mocat:input)

The input schema of a [=simulation model=] is a [=data specification=] that describes how an input dataset of a [=simulation run=] must be structured. A model can have several input schemas, for example for a network, a demand matrix, a run configuration and a scenario.

  • RDF property: mocat:input
  • Range: p-plan:Variable ([=data specification=])

Property: output (mocat:output)

The output schema of a [=simulation model=] is a [=data specification=] that describes how an output dataset of a [=simulation run=] is structured.

  • RDF property: mocat:output
  • Range: p-plan:Variable ([=data specification=])

Property: endpoint URL (dcat:endpointURL)

The endpoint URL of a [=simulation model=] is the root location or primary endpoint of the service through which the model can be run.

  • RDF property: dcat:endpointURL
  • Range: rdfs:Resource

Class: Data Specification (p-plan:Variable)

A data specification describes how a dataset must be structured. Its class is mocat:DataSpecification, a subclass of p-plan:Variable and dcat:Resource ([=cataloged resource=]).

Each input and output of a simulation model can have its own data specification. The input or output data is not necessarily structured as RDF, but the schema must be represented as RDF so that it can be used for automated reasoning about the interoperability of input datasets. Hence, we require an RDF description of the data structure in the form of [[SHACL]] NodeShapes and PropertyShapes. A data specification refers to its NodeShapes with dcterms:hasPart. A NodeShape refers to its PropertyShapes with sh:property. Constraints that cannot be expressed with core SHACL (e.g. topological consistency) are expressed as SHACL-SPARQL constraints (sh:sparql). SHACL-SPARQL does not reuse the Turtle prefix declarations, so the prefixes used in those queries must be declared with sh:declare on an owl:Ontology that is referenced from each constraint with sh:prefixes.

The Traffic Scout example defines five data specifications:

  • omg-schema:TransportNetworkSchema: nodes, edges, turn movements and zones;
  • omg-schema:OriginDestinationMatrixSchema: hourly demand per mode between zones;
  • omg-schema:RunConfigurationSchema: key-value settings with unique keys;
  • omg-schema:TrafficChangeScenarioSchema: create, update and delete operations (ex:changeOperation) on nodes, edges and turn movements;
  • omg-schema:SimulationOutputSchema: simulated flow per edge, mode and hour (output).
<https://data.omgeving.vlaanderen.be/id/shacl/>
    a          owl:Ontology ;
    sh:declare [ sh:prefix    "ex" ;
                 sh:namespace "http://example.org/"^^xsd:anyURI ] ;
    sh:declare [ sh:prefix    "rdf" ;
                 sh:namespace "http://www.w3.org/1999/02/22-rdf-syntax-ns#"^^xsd:anyURI ] .
  
omg-schema:TransportNetworkSchema
    a                   p-plan:Variable ;
    dcterms:title       "Transport Network schema"@en ;

Property: has part (dcterms:hasPart)

A has part of a [=data specification=] is a [[SHACL]] NodeShape that is part of the specification. Each NodeShape targets a class (sh:targetClass), lists its constraints with sh:property and, where core SHACL is insufficient, with sh:sparql.

  • RDF property: dcterms:hasPart
  • Range: sh:NodeShape

Class: Simulation Run (prov:Activity)

A simulation run is a single, complete execution of a [=simulation model=]. Its class is mocat:SimulationRun, a subclass of prov:Activity and dcat:Resource ([=cataloged resource=]). The starting conditions of a run (parameters, random seeds, stopping point) are provided as a run configuration input dataset that conforms to a [=data specification=] of the model; together with the other input datasets, it is linked with prov:used.

Each input and output of a simulation model can have its own [=data specification=]. The data is not necessarily structured as RDF. A semantic asset [[VOCAB-ADMS]] can be used to describe the data structure. In the case of RDF data, [[SHACL]] must be used. 

omg-simulationrun:run-001
    a                        mocat:SimulationRun, prov:Activity ;
    dcterms:title            "Traffic Scout run 001 — Kortrijk 2026-06-01"@en ;
    dcterms:description      "Traffic Scout simulation run on the x-CITE Kortrijk transport network."@en ;
    p-plan:correspondsToStep omg-simulationmodel:traffic-scout ;
    sosa:usedProcedure       omg-simulationmodel:traffic-scout ;
    prov:wasAssociatedWith   omg-agent:traffic-scout-v3-0 ;
    prov:startedAtTime       "2026-06-01T00:00:00Z"^^xsd:dateTime ;
    prov:endedAtTime         "2026-06-01T00:12:59Z"^^xsd:dateTime ;
    prov:used                omg-dataset:xcite-kortrijk-network ;
    prov:used                omg-dataset:xcite-kortrijk-od-demand ;
    prov:used                omg-dataset:run-001-configuration ;
    prov:used                omg-dataset:run-001-traffic-change-scenario ;
    prov:generated           omg-dataset:traffic-scout-output-run-001 .

Property: corresponds to step (p-plan:correspondsToStep)

The corresponds to step property of a [=simulation run=] relates the run to the [=simulation model=] of which it is an execution.

  • RDF property: p-plan:correspondsToStep
  • Range: [=simulation model=]

Property: used procedure (sosa:usedProcedure)

The used procedure property of a [=simulation run=] is an optional alias of p-plan:correspondsToStep, for consumers that interpret runs with [[VOCAB-SSN]].

  • RDF property: sosa:usedProcedure
  • Range: [=simulation model=]

Property: was associated with (prov:wasAssociatedWith)

The was associated with property of a [=simulation run=] refers to the software [=agent=], that is the exact release, that executed the run.

  • RDF property: prov:wasAssociatedWith
  • Range: [=agent=]

Property: started at time (prov:startedAtTime)

The started at time of a [=simulation run=] is the instant at which the run started.

  • RDF property: prov:startedAtTime
  • Range: xsd:dateTime

Property: ended at time (prov:endedAtTime)

The ended at time of a [=simulation run=] is the instant at which the run ended. It is absent while the run is still in progress.

  • RDF property: prov:endedAtTime
  • Range: xsd:dateTime

Property: used (prov:used)

The used property of a [=simulation run=] is a reference to one or more input datasets that were used. Every input dataset must adhere to one of the [=input schema=]s of the [=simulation model=], which is declared with mocat:conformsToSpecification on the dataset.

  • RDF property: prov:used
  • Range: [=dataset=]

Property: generated (prov:generated)

The generated property of a [=simulation run=] is a reference to the output dataset(s) produced by the run. It is the inverse of prov:wasGeneratedBy. The output dataset must adhere to the [=output schema=] of the [=simulation model=].

  • RDF property: prov:generated
  • Range: [=dataset=]

Class: Agent (prov:SoftwareAgent)

An agent is the software package (a specific release of the simulation software) that executed a [=simulation run=]. Its class is mocat:Agent, a subclass of prov:SoftwareAgent and spdx-sw:Package [[SPDX]]. Linking a run to the exact release is essential to reproduce the run.

omg-agent:traffic-scout-v3-0
    a                        mocat:Agent, prov:SoftwareAgent, spdx-sw:Package ;
    foaf:name                "Traffic Scout"@en ;
    spdx-sw:packageVersion   "3.0.4" ;
    spdx-sw:packageUrl       "pkg:tmleuven.be/traffic-scout@3.0.4"^^xsd:anyURI ;
    spdx-sw:downloadLocation <https://intranet.tmleuven.be/tml-leuven/traffic-scout/releases/tag/v3.0.4> ;
    spdx-sw:homePage         <https://intranet.tmleuven.be/tml-leuven/traffic-scout> ;
    spdx-sw:primaryPurpose   spdx-purpose:application .

Property: name (foaf:name)

The name of an [=agent=] is the name of the software.

  • RDF property: foaf:name
  • Range: rdf:langString

Property: package version (spdx-sw:packageVersion)

The package version of an [=agent=] is the release version of the software that executed the run.

  • RDF property: spdx-sw:packageVersion
  • Range: xsd:string

Property: package URL (spdx-sw:packageUrl)

The package URL of an [=agent=] is a package URL (purl) that identifies the release.

  • RDF property: spdx-sw:packageUrl
  • Range: xsd:anyURI

Property: download location (spdx-sw:downloadLocation)

The download location of an [=agent=] is the location from which the release can be downloaded. Not every provider has a public location; in the example it points to an intranet.

  • RDF property: spdx-sw:downloadLocation
  • Range: xsd:anyURI

Property: home page (spdx-sw:homePage)

The home page of an [=agent=] is the home page of the software.

  • RDF property: spdx-sw:homePage
  • Range: xsd:anyURI

Property: primary purpose (spdx-sw:primaryPurpose)

The primary purpose of an [=agent=] is the main purpose of the package, for example spdx-purpose:application.

  • RDF property: spdx-sw:primaryPurpose
  • Range: spdx-sw:SoftwarePurpose

Class: Dataset (dcat:Dataset)

A dataset is defined in [[VOCAB-DCAT-3]] as a collection of data, published or curated by a single agent, and available for access or download in one or more representations. A dataset is a [=cataloged resource=]. In MoCAT, all inputs (network, demand matrix, run configuration, scenario) and outputs of a [=simulation run=] are datasets.

omg-dataset:xcite-kortrijk-network
    a                             dcat:Dataset ;
    dcterms:title                 "xCite Kortrijk Transport network"@en ;
    dcterms:description           """This dataset contains a routable transport network extended with traffic-light control schemes and local information."""@en ;
    dcat:keyword                  "transport network"@en, "OpenStreetMap"@en ;
    dcat:theme                    <http://publications.europa.eu/resource/authority/data-theme/TRAN> ;
    dcat:theme                    <http://www.eionet.europa.eu/gemet/concept/11087> ;

Property: has distribution (dcat:distribution)

The has distribution property of a [=dataset=] refers to an available representation of the dataset, for example a downloadable GeoJSON file.

  • RDF property: dcat:distribution
  • Range: [=distribution=]

Property: conforms to specification (mocat:conformsToSpecification)

The conforms to specification property of a [=dataset=] is a reference to the [=data specification=] the dataset adheres to. It is a sub-property of dcterms:conformsTo, so that generic DCAT consumers can still interpret it.

  • RDF property: mocat:conformsToSpecification
  • Range: [=data specification=]

Property: corresponds to variable (p-plan:correspondsToVariable)

The corresponds to variable property of a [=dataset=] relates the dataset to the P-PLAN variable (the [=data specification=]) that it instantiates. In the example it always has the same value as mocat:conformsToSpecification.

  • RDF property: p-plan:correspondsToVariable
  • Range: [=data specification=]

Property: was generated by (prov:wasGeneratedBy)

The was generated by property of a [=dataset=] is a reference to the [=simulation run=] that generated the output dataset. This output dataset must adhere to the [=output schema=] of the [=simulation model=]. Producers should assert both prov:wasGeneratedBy on the dataset and prov:generated on the run, as consumers may traverse either direction.

  • RDF property: prov:wasGeneratedBy
  • Range: [=simulation run=]

Property: was derived from (prov:wasDerivedFrom)

The was derived from property of a [=dataset=] refers to a dataset from which it was derived, for example a scenario dataset derived from the transport network it modifies.

  • RDF property: prov:wasDerivedFrom
  • Range: [=dataset=]

Open API specification

The Simulation Model API makes it possible to configure and start a [=simulation run=] of a [=simulation model=] in a standardized way. Execution is asynchronous (see ). The API specification openapi.yaml can be viewed via the swagger-editor.html.

Implementation report

Metadata creation

Departement Omgeving wants to have an overview of all simulation models that are used in public service delivery. Simulation models are mainly used for environmental impact assessment.

We will incorporate the creation of metadata for simulation models by embedding this in the software development lifecycle of the simulation model. A release of a new version of the simulation model by the software build engine will trigger the creation of a new metadata record that will be included in a Triplestore. The triple store is schema-free and enables various use cases. Use case 12 in WP4 of the [[X-CITE-P-PLAN]] citiverse project.

Metadata will be available on the Linked Data service of Departement Omgeving at https://data.omgeving.vlaanderen.be/#sparqlForm. The metadata can there be explored from a plain SPARQL interface. 

PREFIX prov: <http://www.w3.org/ns/prov#>
SELECT ?s ?p ?o
WHERE {
  ?s a prov:Plan .
  ?s ?p ?o
}

Metadata publication and harvesting

We will publish a limited subset of the metadata as ISO19115 metadata records using the Geonetwork catalog. This catalog provides a configurable facetted search functionality via ElasticSearch. The catalog has standard APIs that are used to harvest metadata records. One downside of the use of ISO19115 metadata records is that not all metadata fields in MoCAT can be mapped to this standard.

Test interoperability of input data

For each input of a simulation model, the [=data specification=] contains SHACL shapes. A dataset is interoperable with an input of the model if it declares mocat:conformsToSpecification with the expected data specification and its RDF representation validates against the referenced shapes (including the SHACL-SPARQL constraints). For non-RDF distributions (GeoJSON, CSV, JSON), the distribution is first converted to RDF before validation.

Start a simulation run via a universal interface

We will implement the Simulation Model API to start simulation runs and assess the impact of scenarios of future land use change on emission of greenhouse gasses.
